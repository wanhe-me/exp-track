## 1. 项目介绍

### 1.1 背景

在个人工作与生活中，我们往往同时订阅了多个包年包月服务：大模型 API（如 OpenAI、Claude、Gemini）、各类 SaaS 工具、流媒体会员、云资源套餐、网盘、域名/SSL、软件授权等。这些订阅的**到期时间、扣费周期、价格**分散在不同平台的通知邮件里，极易被遗忘，导致：

- 忘记续费造成服务中断（如关键 API Key 失效）；
- 忘记取消造成持续自动扣费，产生不必要的开支；
- 无法从全局视角掌握"哪些服务即将到期"，进而造成浪费。

> **核心痛点聚焦**：本产品最核心的问题是"**不知道都有哪些服务、什么时候过期，进而导致浪费**"。至于"到底花了多少钱"属于次要诉求，相关统计能力在本阶段做最小化处理。

### 1.2 产品定位

**exp-track（单用户版）** 是一个**本地优先的订阅到期追踪与可视化网站**。用户将所有包年/包月订阅信息集中录入，系统基于到期时间进行统一管理与可视化展示，帮助用户：

- 在一个看板中掌握所有订阅的剩余天数、状态与费用；
- 在订阅即将到期前得到醒目的页面提示；
- 通过图表直观了解未来到期时间分布。

> **通用性定位**：虽然产品灵感来源于追踪大模型 API 订阅，但产品定位为**通用的包年/包月订阅到期追踪工具**，适用于任何周期性付费服务的到期管理场景。为保持通用性，产品**坚持手动填写与维护**，不引入过度自动化（如自动续期、自动计算到期日、自动抓取账单等），避免限制产品适用范围。

> **部署定位**：本版本为**单用户单实例**，数据存储在本地，无多用户、无鉴权体系。部署方式上同时提供「快速部署（SQLite，无需容器）」与「稳定部署（MySQL）」两种路径，以最大化个人本地使用的便利性。

### 1.3 目标用户

- **核心用户（个人）**：
  - 个人开发者、独立创作者：管理大模型 API / 工具类订阅；
  - 任何希望掌握自身订阅到期情况的个人用户（适用于任何包年/包月服务）。

### 1.4 核心特性

> 特性按 MVP 优先级标注。**P0** 为核心价值（必须完成），**P1** 为辅助特性（应完成），**P2** 为可后置。

| 特性 | 优先级 | 说明 |
|------|--------|------|
| 订阅录入 | P0 | 手动添加订阅：名称、类别、价格、计费周期（月/季/年）、开始日期、到期日期、是否自动续费、备注。 |
| 到期看板 | P0 | 以卡片/列表形式展示所有订阅，按"剩余天数"排序，突出临期与已过期项。 |
| 状态标识 | P0 | 已过期/7天内到期/30天内到期/充足 四档状态，颜色区分。阈值通过配置文件定义。 |
| 临期提醒 | P0 | 基于到期时间，在前端以醒目标识提示即将到期的订阅（页面内提示，无推送）。 |
| 可视化统计 | P1（辅助） | **本阶段仅做"未来到期时间轴"一张图**，直接服务于"什么时候过期"的核心痛点。其余图表后置。 |
| 灵活部署 | P0 | 提供**快速部署**（SQLite，开箱即用）与**稳定部署**（MySQL）两种方式，数据均保存在本地，无第三方云服务依赖。 |

### 1.5 技术架构概览

项目采用**单仓库前后端分离**结构：

- **前端**：Vue 3 + Vite + TypeScript，使用 Pinia 状态管理、Vue Router 路由、ECharts 图表、Day.js 时间处理。
- **后端**：Express 5 + TypeScript，提供 REST API，统一响应信封契约。
- **数据库（可切换）**：
  - **快速部署**：使用嵌入式数据库 **SQLite**（文件型，无需安装数据库服务，零外部依赖）；
  - **稳定部署**：使用 **MySQL 8.0**（通过 Docker Compose 或直接连接既有 MySQL 实例）。
  - 后端通过数据访问层（DAL）抽象屏蔽两种数据库的差异，业务代码不感知底层数据库类型。
- **配置驱动**：状态阈值、日期格式、货币符号等可调参数集中存放于配置文件，虽为硬编码但可随时修改，无需改动业务代码。

> **DAL 抽象风险提示**：SQLite 与 MySQL 存在方言差异（日期函数、自增主键、布尔类型、JSON 字段等），DAL 层需在开发期重点关注并充分测试，确保两种数据库行为一致。

### 1.6 范围说明

- **本期范围**：
  - 面向**个人用户**的订阅增删改查、到期看板、临期页面提醒；
  - 单张可视化图表（未来到期时间轴）；
  - 两种本地部署方式（快速部署/稳定部署）；
  - 单用户、单实例的本地数据存储；
  - 软删除+归档机制。
- **非本期范围**（纳入配套 PRD `expTrack_Team_PRD.md`）：
  - 小型团队多人协作：多用户账户、登录鉴权、共享看板、成员权限管理；
  - 邮件/短信/Webhook 主动推送提醒；
  - 订阅自动抓取（对接第三方账单 API）；
  - 数据导入/导出及自动数据迁移工具；
  - 多币种与汇率转换；
  - 月度支出统计及类别占比等扩展图表；
  - 移动端原生应用与 Web 响应式适配。

## 2. 部署要求

产品需支持**纯本地部署**：数据保存在用户自有环境，不依赖任何第三方云服务，以保障隐私。为兼顾不同用户的机器环境，要求提供两种部署模式：

| 部署模式 | 适用场景 | 容器环境 | 数据库 | 复杂度 |
|----------|----------|----------|--------|--------|
| **快速部署** | 个人本地试用，机器无 Docker/容器，希望开箱即用 | 不需要 | SQLite（文件型，零依赖） | 低 |
| **稳定部署** | 具备 MySQL 环境（本机或已有实例），追求数据稳定性与可维护性 | 可选（推荐 Docker） | MySQL 8.0 | 中 |

**要求明细：**

- 两种模式共用同一套前端/后端代码，底层数据库类型对用户与业务代码透明，通过配置切换；
- 个人用户**默认推荐快速部署**，无需安装任何数据库服务即可运行，数据以单文件形式存放，便于备份与迁移；
- 当数据量增长或需要数据库级管理时，可切换至稳定部署；
- 部署过程对用户友好，安装/配置/启动步骤应最小化，降低个人本地使用的门槛。

> **部署模式切换路径**：本版本不提供自动数据迁移工具。两种模式之间的数据迁移通过"未来版本提供导入/导出工具"实现。

## 4. 数据模型

> 本节定义核心实体字段。类型标注兼顾 SQLite/MySQL，具体 SQL 方言映射由 DAL 层处理。

### 4.1 订阅实体 `subscription`

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `id` | INTEGER（自增主键） | 是 | - | 主键 |
| `name` | VARCHAR(100) | 是 | - | 订阅名称 |
| `category_id` | INTEGER（外键） | 是 | - | 关联 `category.id` |
| `price` | DECIMAL(10,2) | 是 | - | 价格，单位：人民币元 |
| `billing_cycle` | VARCHAR(16) | 是 | - | 枚举：`month`/`quarter`/`year` |
| `start_date` | DATE | 是 | - | 开始日期 `YYYY-MM-DD` |
| `expire_date` | DATE | 是 | - | **到期日期（核心字段）** |
| `auto_renew` | BOOLEAN | 是 | `false` | 是否自动续费（**纯标记**，不触发自动逻辑） |
| `note` | TEXT | 否 | NULL | 备注 |
| `archived` | BOOLEAN | 是 | `false` | 是否归档 |
| `deleted_at` | TIMESTAMP | 否 | NULL | 软删除时间，NULL 表示未删除 |
| `created_at` | TIMESTAMP | 是 | 当前时间 | 创建时间 |
| `updated_at` | TIMESTAMP | 是 | 当前时间 | 更新时间 |

### 4.2 分类实体 `category`

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `id` | INTEGER（自增主键） | 是 | - | 主键 |
| `name` | VARCHAR(50) | 是 | - | 分类名称，唯一 |
| `created_at` | TIMESTAMP | 是 | 当前时间 | 创建时间 |
| `updated_at` | TIMESTAMP | 是 | 当前时间 | 更新时间 |

> 分类不做软删除：删除前需确保无订阅引用（见 FR-10）。

### 4.3 软删除与归档查询约定

- **默认视图查询条件**：`deleted_at IS NULL AND archived = false`；
- **已归档视图查询条件**：`deleted_at IS NULL AND archived = true`；
- **已删除视图（恢复用）查询条件**：`deleted_at IS NOT NULL`。

## 5. 配置项

> 可调参数集中存放于配置文件（前后端各有一份对应配置，保持一致）。虽为硬编码，但修改配置无需改动业务代码。

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| `statusThresholds.soon7` | 7 天内到期阈值（天） | `7` |
| `statusThresholds.soon30` | 30 天内到期阈值（天） | `30` |
| `timeline.rangeDays` | 未来到期时间轴展示范围（天） | `90` |
| `dateFormat` | 日期展示格式 | `YYYY-MM-DD` |
| `currencySymbol` | 货币符号 | `¥` |
| `timezone` | 时区处理（默认本地） | `local` |

> 状态阈值定义：剩余天数 < 0 → 已过期；0 ~ `soon7` → 7 天内；`soon7+1` ~ `soon30` → 30 天内；> `soon30` → 充足。

## 6. 非功能需求

### 6.1 性能与容量

- 预期数据量：几十 ~ 100 条订阅；
- 无需分页/虚拟滚动；
- 看板首屏渲染应流畅，列表与图表加载无明显延迟。

### 6.2 兼容性

- 目标浏览器：Chrome/Edge/Firefox/Safari 最新版；
- **以桌面端为主**，响应式适配列入后续规划。

### 6.3 数据安全与备份

- 数据保存在本地，无第三方云服务依赖；
- SQLite 单文件存在损坏风险，建议用户定期手动备份数据库文件。

### 6.4 国际化

- 本版本仅支持中文界面，国际化框架预留但不实现。

## 7. 工程规范

> 本章节约束项目目录结构、公共样式、公共组件与接口扩展原则，目的是**保持视觉一致性、减少重复造轮子、降低维护成本**。

### 7.1 目录结构规范

项目采用单仓库前后端分离，推荐结构如下：

```
exp-track/
├── backend/                       # 后端
│   └── src/
│       ├── config/                # 配置项（状态阈值等）
│       ├── dal/                   # 数据访问层（SQLite/MySQL 抽象）
│       ├── routes/                # 路由定义
│       ├── controllers/           # 控制器（请求/响应处理）
│       ├── services/              # 业务逻辑
│       ├── middlewares/           # 中间件
│       ├── types/                 # 共享类型
│       ├── utils/                 # 工具函数
│       └── app.ts                 # 应用入口
├── src/                           # 前端（Vue 3 + Vite + TypeScript）
│   ├── lib/                       # 底层库/基础设施（Axios 实例、unwrap 等）
│   ├── api/                       # 按业务域组织的接口调用
│   ├── assets/styles/             # 公共样式、设计令牌
│   ├── components/                # 公共组件
│   │   ├── base/                  # 基础原子组件
│   │   └── ...                    # 业务组件
│   ├── composables/               # 组合式函数
│   ├── layouts/                   # 布局组件
│   ├── router/                    # 路由
│   ├── stores/                    # Pinia 状态管理
│   ├── views/                     # 页面
│   ├── types/                     # 前端类型定义
│   ├── utils/                     # 工具函数
│   ├── App.vue                    # 根组件
│   └── main.ts                    # 应用入口
└── ...
```

**约束**：

- 公共能力（样式、组件、工具函数、类型）按上述目录归口，**禁止在业务页面内重复定义同类能力**；
- `lib/` 与 `api/` 职责边界：`lib/` 提供底层请求能力，`api/` 仅按业务域编排接口调用；
- 共享领域类型/配置前后端各一份，靠约定同步；
- `components/base/` 放无副作用的原子组件；跨页面复用的业务组件置于 `components/` 根。

### 7.2 公共样式与设计令牌

- **设计令牌（CSS 变量）**统一在 `src/assets/styles/` 下定义，至少包含色彩、间距、圆角、阴影、字号、行高。
- **状态色映射**由设计令牌统一管理：

| 状态 | 建议色 |
|------|--------|
| 已过期 | 红 |
| 7 天内到期 | 橙 |
| 30 天内到期 | 黄 |
| 充足 | 灰/绿 |

- 全局基础样式（reset、排版）统一管理，业务组件样式仅写自身差异化部分。

### 7.3 公共组件

- 重复出现的 UI 单元**必须抽取为公共组件**，放入 `src/components/`（基础原子组件放 `base/`）；
- 本阶段应抽取的公共组件（不限于）：`StatusBadge`、`SubscriptionCard`、`CategoryTag`、`ConfirmDialog`、`EmptyState`、通用表单控件封装；
- 公共组件应 **props 驱动、无副作用**。

### 7.4 视觉一致性原则

- 同类元素全站视觉统一；
- 颜色、间距、圆角、字号**只能使用设计令牌**，禁止散落硬编码；
- 新增页面/组件须复用既有公共组件。

### 7.5 接口扩展原则

> **核心原则：能对现有接口进行改造兼容的，不要新增接口。**

- **优先扩展现有接口**：新需求优先通过在现有端点上**新增可选字段/可选参数**实现；
- **向后兼容**：新增字段只增不删，旧客户端不受影响；废弃字段需保留过渡期并标注；
- **统一响应信封**：所有接口遵循统一响应结构，不得为单个接口自定义格式；
- **RESTful 命名规范**：资源命名统一、动词语义清晰；
- **接口合并**：功能相近的查询接口优先合并（通过参数区分）；
- **新增接口需评估**：确需新增接口时，需记录决策原因。
