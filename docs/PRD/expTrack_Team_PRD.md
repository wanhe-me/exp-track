# exp-track 产品需求文档 — 小型团队多人协作版

> 版本：v0.1（规划中）
> 状态：需求草案，待开发
> 最后更新：2026-07-28
> 阶段定位：**小型团队·多人协作·共享订阅管理**
>
> 此文档定义 exp-track **从单用户单实例扩展到小型团队多人协作**的产品需求范围与方案。
> 前置条件：单用户单实例版（`expTrack_SingleUser_PRD.md`）功能开发完成并稳定运行。
> 本版本是单用户版的**功能扩展**，非独立产品，所有单用户版已有功能（订阅管理、看板、数据模型等）在此不再重复，仅描述**增量需求**。

---

## 1. 项目介绍

### 1.1 背景

exp-track 单用户版解决了个人用户的订阅到期管理问题。但在实际工作场景中，小型团队（如 2~10 人创业团队、小型工作室、部门小组）往往共同使用同一批订阅服务（如共享的工具订阅、团队 API 额度、云资源套餐等），面临以下额外痛点：

- 团队共用的订阅**实际由谁管理、谁来续费**不清晰，责任无归属；
- 成员离职或交接时，共享订阅的管理权限丢失或混乱；
- 无法为团队领导提供所有共享订阅的到期全景视图；
- 管理员无法限制普通成员对订阅的编辑/删除权限。

### 1.2 产品定位

**exp-track 团队版** 是在单用户单实例版本的基础上，为小型团队提供**多用户账户、登录鉴权、团队空间、成员权限管理**等协作能力。核心设计理念：

- **团队即共享空间**：每个团队成员各自管理**个人视角的订阅**，同时共享**团队共用的订阅看板**；
- **轻量级团队权限**：不追求企业级 RBAC（角色基权限），仅做"管理员/成员"两级区分；
- **延续本地部署传统**：团队版仍支持私有化部署，不强制上云。

### 1.3 目标用户

- **小团队管理员**（2~10 人）：管理团队共用订阅，监控团队工具资源的到期状态；
- **小团队成员**：查看共享订阅到期情况，接收临期提醒；
- **小型企业/工作室**：需要一个轻量级的团队订阅管理工具，不愿意使用笨重的企业 ITIL 系统。

### 1.4 核心特性（团队增量）

| 特性 | 优先级 | 说明 |
|------|--------|------|
| 用户注册与登录 | P0 | 邮箱/密码注册登录，JWT Token 鉴权 |
| 团队空间管理 | P0 | 创建/加入/退出团队，团队基本设置 |
| 订阅归属（个人/团队） | P0 | 订阅可归属个人或团队，团队可见范围受权限控制 |
| 两级权限（管理员/成员） | P0 | 管理员可管理团队订阅与成员，成员仅可查看和备注 |
| 团队共享看板 | P0 | 团队管理层展示所有成员可见的共享订阅到期状态 |
| 成员管理 | P1 | 管理员邀请/移除成员，成员角色分配 |
| 订阅变更记录（操作日志） | P1 | 记录谁在何时创建/编辑/删除了团队订阅 |
| 团队通知与提醒 | P2 | 临期订阅通过页面通知全体团队成员 |

### 1.5 架构变更概览

> 基于单用户版架构，新增以下组件：

- **前端新增**：登录/注册页面、团队管理页面、用户个人设置、角色感知的路由守卫；
- **后端新增**：
  - 用户认证模块（注册/登录/Token 刷新）；
  - 团队管理模块（创建/加入/退出/成员管理）；
  - 中间件（JWT 鉴权、角色校验）；
- **数据库新增表**：`users`、`teams`、`team_members`、`operation_logs`；
- **现有表扩展**：`subscription` 表新增 `owner_type`（`personal`/`team`）、`team_id`、`owner_id` 字段。

### 1.6 范围说明

- **本期范围（团队 v1）**：
  - 用户注册登录 + JWT 鉴权；
  - 团队创建/成员邀请与移除；
  - 订阅归属（个人/团队双层模型）；
  - 管理员/成员两级权限控制；
  - 团队共享看板。
- **非本期范围**：
  - 多团队同时归属（用户同时加入多个团队，本期仅支持一个活跃团队）；
  - 细粒度 RBAC 自定义角色；
  - SAML/OAuth/SSO 企业集成（如飞书、企业微信登录）；
  - 团队间订阅分享/跨团队协作；
  - 团队账单分摊（按成员计算费用）；
  - 移动端原生应用/响应式适配。

> 单用户版已有的功能（订阅增删改、归档恢复、时间轴、自定义分类等）在团队版中继承，不再重复叙述。

## 2. 部署要求

### 2.1 单实例多用户架构

团队版仍为**单实例部署**（一个后端服务+一个数据库实例），但支持**多用户同时使用**。这意味着：

- 部署方式与单用户版一致（快速部署 SQLite / 稳定部署 MySQL），架构不改变；
- 不引入微服务/分布式，保持低成本部署；
- 单实例需能够承载 10~50 用户、每条用户 50~200 条订阅的数据规模。

### 2.2 安全需求

- 用户密码必须加盐哈希存储（bcrypt/argon2），禁止明文；
- JWT Token 需设置过期时间与刷新机制，Token 泄露可被服务端吊销（维护黑名单或短有效期+刷新）；
- 接口鉴权中间件保护所有团队相关端点，禁止未登录访问；
- 禁止越权访问其他团队的订阅数据（通过 `team_id` + `user_id` 双重校验）。

## 3. 功能需求

### FR-T01: 用户注册与登录

| 项目 | 内容 |
|------|------|
| 优先级 | P0 |
| 描述 | 用户通过邮箱+密码注册账号，注册后自动创建个人空间；通过邮箱+密码登录获得 Token。 |
| 字段 | 邮箱（唯一）、密码（加密存储）、昵称（选填） |
| 校验 | 邮箱格式合法；密码长度 ≥ 8，须含字母+数字；注册时邮箱唯一校验 |
| Token | JWT，有效期 24 小时，提供 Refresh Token 机制（7 天） |
| 安全 | 连续 5 次登录失败临时锁定 15 分钟（可选，抗暴力破解） |

### FR-T02: 团队创建与管理

| 项目 | 内容 |
|------|------|
| 优先级 | P0 |
| 描述 | 已注册用户可创建团队（成为该团队管理员），填写团队名称、简介。 |
| 字段 | 团队名称（≤50，唯一）、简介（≤200，选填） |
| 限制 | 一个用户同时只能是一个团队的活跃成员（即不可同时归属多个团队，可切换）。支持解散团队（管理员权限，解散后所有数据标记为不可见）。 |

### FR-T03: 成员邀请与加入

| 项目 | 内容 |
|------|------|
| 优先级 | P1 |
| 描述 | 管理员可通过邮箱邀请用户加入团队。被邀请用户收到邀请后确认加入。 |
| 流程 | 管理员输入被邀请人邮箱 → 系统发送邀请（站内通知，不上邮件推送）→ 被邀请人登录后在"我的邀请"中确认/拒绝 → 确认后成为团队成员（默认角色：成员）。 |
| 替代路径 | 管理员也可直接在"成员管理"中搜索已注册用户并直接添加。 |

### FR-T04: 成员角色与权限

| 项目 | 内容 |
|------|------|
| 优先级 | P0 |
| 描述 | 两级角色：**管理员** / **成员**。 |
| 权限矩阵 | |

| 操作 | 管理员 | 成员 |
|------|--------|------|
| 查看团队订阅 | ✅ | ✅ |
| 添加团队订阅 | ✅ | ❌ |
| 编辑团队订阅 | ✅ | ❌ |
| 删除/归档团队订阅 | ✅ | ❌ |
| 管理团队成员（邀请/移除/改角色）| ✅ | ❌ |
| 解散团队 | ✅ | ❌ |
| 个人订阅管理 | ✅ | ✅ |
| 添加备注/标记（个人标注）| ❌ | ✅（仅可加个人备注，不修改订阅本身）|

### FR-T05: 订阅归属模型（个人/团队双层）

| 项目 | 内容 |
|------|------|
| 优先级 | P0 |
| 描述 | 订阅区分"个人订阅"（仅创建者可见）与"团队订阅"（团队可见）。 |
| 字段扩展 | `subscription` 表新增 `owner_type`（枚举：`personal` / `team`）、`owner_id`（用户 ID 或团队 ID） |
| 个人订阅 | 行为与单用户版完全一致，仅创建者可见、可操作。 |
| 团队订阅 | 由管理员创建/编辑/删除，**全体团队成员只读查看**，成员可添加个人备注（不影响订阅本身）。 |

### FR-T06: 团队共享看板

| 项目 | 内容 |
|------|------|
| 优先级 | P0 |
| 描述 | 团队管理页面展示该团队所有共享订阅的到期看板，与个人看板布局一致但仅包含团队订阅。 |
| 排序 | 与 FR-05 一致：按剩余天数升序，已过期置顶。 |
| 筛选 | 支持按类别/状态筛选。 |
| 权限 | 成员进入团队看板自动加载该团队的共享订阅。 |

### FR-T07: 个人主页与团队主页切换

| 项目 | 内容 |
|------|------|
| 优先级 | P0 |
| 描述 | 登录后用户可自由切换"个人空间"与"团队空间"。导航栏增加团队切换入口。 |
| 个人空间 | 展示该用户个人订阅（与单用户版行为一致）。 |
| 团队空间 | 展示该用户所属团队的共享订阅。 |

### FR-T08: 操作日志

| 项目 | 内容 |
|------|------|
| 优先级 | P1 |
| 描述 | 记录团队订阅的所有关键操作（创建、编辑、删除、归档恢复），供管理员审计。 |
| 字段 | 操作人、操作时间、操作类型（create/update/delete/archive/restore）、目标订阅 ID、变更前后摘要 |
| 展示 | 团队设置页内以表格展示，按时间倒序，保留最近 90 天。 |

### FR-T09: 团队通知

| 项目 | 内容 |
|------|------|
| 优先级 | P2 |
| 描述 | 团队订阅到期时，相关提醒会出现在所有团队成员的个人提醒区。基于单用户版已有的页面提醒机制。 |
| 范围 | 仅团队订阅触发团队通知。个人订阅的提醒仅本人可见。 |

## 4. 数据模型（增量）

> 以下为团队版新增/变更的表及字段。单用户版已有表不变。

### 4.1 用户表 `users`

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `id` | INTEGER（自增主键） | 是 | - | 主键 |
| `email` | VARCHAR(255) | 是 | - | 邮箱，唯一 |
| `password_hash` | VARCHAR(255) | 是 | - | 加盐哈希后的密码 |
| `nickname` | VARCHAR(50) | 否 | NULL | 用户昵称 |
| `active_team_id` | INTEGER | 否 | NULL | 当前活跃团队 ID（用户同时仅归属一个活跃团队） |
| `created_at` | TIMESTAMP | 是 | 当前时间 | 创建时间 |
| `updated_at` | TIMESTAMP | 是 | 当前时间 | 更新时间 |

### 4.2 团队表 `teams`

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `id` | INTEGER（自增主键） | 是 | - | 主键 |
| `name` | VARCHAR(50) | 是 | - | 团队名称，唯一 |
| `description` | VARCHAR(200) | 否 | NULL | 简介 |
| `created_by` | INTEGER（外键） | 是 | - | 创建者用户 ID（自动成为管理员） |
| `created_at` | TIMESTAMP | 是 | 当前时间 | 创建时间 |
| `updated_at` | TIMESTAMP | 是 | 当前时间 | 更新时间 |

### 4.3 团队成员表 `team_members`

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `id` | INTEGER（自增主键） | 是 | - | 主键 |
| `team_id` | INTEGER（外键） | 是 | - | 关联 `teams.id` |
| `user_id` | INTEGER（外键） | 是 | - | 关联 `users.id` |
| `role` | VARCHAR(16) | 是 | `member` | 枚举：`admin` / `member` |
| `joined_at` | TIMESTAMP | 是 | 当前时间 | 加入时间 |

> `(team_id, user_id)` 联合唯一。

### 4.4 操作日志表 `operation_logs`

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `id` | INTEGER（自增主键） | 是 | - | 主键 |
| `team_id` | INTEGER（外键） | 是 | - | 关联 `teams.id` |
| `user_id` | INTEGER（外键） | 是 | - | 操作人 |
| `subscription_id` | INTEGER（外键） | 否 | NULL | 目标订阅 ID |
| `action` | VARCHAR(32) | 是 | - | 枚举：`create`/`update`/`delete`/`archive`/`restore` |
| `summary` | TEXT | 否 | NULL | 变更摘要（如"修改价格从 ¥100 为 ¥120"） |
| `created_at` | TIMESTAMP | 是 | 当前时间 | 操作时间 |

### 4.5 订阅表字段扩展

`subscription` 表新增字段（向后兼容，现有单用户数据不受影响）：

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `owner_type` | VARCHAR(16) | 是 | `personal` | 枚举：`personal` / `team` |
| `owner_id` | INTEGER | 是 | - | 个人订阅=用户 ID，团队订阅=团队 ID |

> 单用户版已有数据自动满足 `owner_type='personal'`、`owner_id` 默认可设置为 0（或数据库层设逻辑默认值）。

## 6. 非功能需求（增量）

### 6.1 性能

- 预期数据量：10~50 用户 × 50~200 条订阅/人，总计不超过 10,000 条订阅；
- 需分页的接口（如操作日志）支持 LIMIT/OFFSET 或游标分页；
- 看板加载耗时（含权限过滤）不超过 1 秒。

### 6.2 安全

- 所有需要身份认证的接口统一经 JWT 中间件；
- 敏感信息传输使用 HTTPS（生产环境）；
- 用户密码禁止明文存储；
- 团队订阅的 API 查询必须过滤 `team_id`，防止跨团队越权访问；
- 前端 Token 过期自动刷新或跳转登录页。

### 6.3 数据兼容性

- 团队版的数据库 schema 必须向后兼容单用户版（`subscription` 表新增字段有默认值，旧数据无需迁移即可升级）；
- 单用户版升级到团队版时，部署脚本应自动执行新增表的创建与字段迁移。

### 6.4 兼容性

- 与单用户版相同的浏览器兼容目标；
- **仍以桌面端为主**。

### 6.5 国际化

- 本阶段仍仅支持中文，国际化框架可沿用单用户版的预留。

### 7.3 接口扩展原则（补充）

- 所有团队版新增接口遵循统一响应信封，与单用户版一致；
- 需要鉴权的接口在 Header 携带 `Authorization: Bearer <token>`；
- 接口路径遵循 RESTful 风格：
  - `POST /api/auth/register` — 注册
  - `POST /api/auth/login` — 登录
  - `POST /api/auth/refresh` — 刷新 Token
  - `POST /api/teams` — 创建团队
  - `GET /api/teams/:id/members` — 成员列表
  - `POST /api/teams/:id/members` — 添加成员
  - `DELETE /api/teams/:id/members/:userId` — 移除成员

### 7.4 数据库迁移

- 团队版首次部署时自动建表（沿用单用户版 DAL 的自动建表机制）；
- 从单用户版升级到团队版需提供 SQL 迁移脚本（`migrations/001_add_team_tables.sql`），由部署脚本执行。

## 8. 验收标准

> 以下为团队版的验收检查项，单用户版验收标准（第 8 章）仍整体适用。

- [ ] 用户可注册、登录、退出，登录状态持久化
- [ ] 未登录用户无法访问需要鉴权的页面和 API（重定向到登录页或 401）
- [ ] JWT Token 过期自动刷新或触发重新登录
- [ ] 可创建团队并自动成为管理员
- [ ] 管理员可添加/移除成员
- [ ] 被移除成员的账号仍可独立使用个人空间
- [ ] 团队成员可在两个空间之间切换：个人空间 vs 团队空间
- [ ] 团队订阅仅管理员可增删改，成员只读
- [ ] 个人订阅对团队其他成员完全不可见
- [ ] 团队成员在团队看板中可看到所有共享订阅
- [ ] 操作日志正确记录团队订阅变更行为
- [ ] 团队版升级脚本可正确迁移单用户版数据（`subscription` 表新增字段有默认值）
- [ ] SQLite 与 MySQL 两种部署模式下团队功能均正常工作

## 9. 实施建议

### 9.1 阶段划分

| 阶段 | 范围 | 建议工作量 |
|------|------|-----------|
| **团队 v1.0**（核心） | FR-T01 ~ FR-T07（注册登录、团队管理、订阅归属、共享看板） | ★★★★（较重） |
| **团队 v1.1**（增强） | FR-T08 操作日志 + FR-T09 团队通知 | ★★（较轻） |
| **后续** | 多团队归属、OAuth/SSO、计费分摊等（见 1.6 非本期范围） | — |

### 9.2 依赖关系

- 团队版所有功能依赖 FR-T01（用户注册与登录），所以**认证模块是团队版的基石**，建议最先开发；
- FR-T05（订阅归属模型）是核心数据模型变更，需在 FR-T02 之前或同步完成数据库表结构扩展；
- 团队功能可先在前端路由层面添加守卫，等后端 API 完成后桥接。

### 9.3 向后兼容策略

- `subscription` 表新增 `owner_type` 和 `owner_id` 字段需设置默认值（`owner_type='personal'`, `owner_id=0`），确保现有单用户版数据不报错；
- 单用户版数据库直接升级到团队版时，现有全部订阅自动归入首个用户的个人空间；
- 前端原有页面（未登录时）保持与单用户版一致的行为；登录后导航栏增加入口。
