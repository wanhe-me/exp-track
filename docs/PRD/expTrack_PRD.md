## 1. 项目介绍

### 1.1 背景

在个人与工作场景中，我们往往同时订阅了多个包年包月服务：大模型 API（如 OpenAI、Claude、Gemini）、各类 SaaS 工具、流媒体会员、云资源套餐、网盘、域名/SSL、软件授权等。这些订阅的**到期时间、扣费周期、价格**分散在不同平台的通知邮件里，极易被遗忘，导致：

- 忘记续费造成服务中断（如关键 API Key 失效）；
- 忘记取消造成持续自动扣费，产生不必要的开支；
- 无法从全局视角掌握"哪些服务即将到期"，进而造成浪费。

> **核心痛点聚焦**：本阶段最核心的问题是"**不知道都有哪些服务、什么时候过期，进而导致浪费**"。至于"到底花了多少钱"属于次要诉求，相关统计能力在本阶段做最小化处理。

### 1.2 产品定位

**exp-track** 是一个**本地优先的订阅到期追踪与可视化网站**。用户将所有包年/包月订阅信息集中录入，系统基于到期时间进行统一管理与可视化展示，帮助用户：

- 在一个看板中掌握所有订阅的剩余天数、状态与费用；
- 在订阅即将到期前得到提醒；
- 通过图表直观了解未来到期时间分布。

> **通用性定位**：虽然产品灵感来源于追踪大模型 API 订阅，但产品定位为**通用的包年/包月订阅到期追踪工具**，适用于任何周期性付费服务的到期管理场景。为保持通用性，产品**坚持手动填写与维护**，不引入过度自动化（如自动续期、自动计算到期日、自动抓取账单等），避免限制产品适用范围。

> **阶段定位（MVP 第一阶段）**：当前版本为 **MVP 测试阶段**，**优先解决个人用户**的订阅到期管理需求。本阶段**不纳入小型团队的多人协作场景**（无多账户、无共享/权限体系），相关能力列入后续规划。部署方式上同时提供「快速部署（无需容器）」与「稳定部署（MySQL）」两种路径，以最大化个人本地使用的便利性。

### 1.3 目标用户

- **本阶段核心用户（个人）**：
  - 个人开发者、独立创作者：管理大模型 API / 工具类订阅；
  - 任何希望掌握自身订阅到期情况的个人用户（适用于任何包年/包月服务）。
- **暂不在本阶段范围**：小团队管理员（团队共用订阅的多人协作、共享看板、权限管理），详见 1.6 范围说明。

### 1.4 核心特性

> 特性按 MVP 优先级标注。**P0** 为核心价值（必须完成），**P1** 为辅助特性（应完成），**P2** 为可后置。

| 特性 | 优先级 | 说明 |
|------|--------|------|
| 订阅录入 | P0 | 手动添加订阅：名称、类别、价格、计费周期（月/季/年）、开始日期、到期日期、是否自动续费、备注。 |
| 到期看板 | P0 | 以卡片 / 列表形式展示所有订阅，按"剩余天数"排序，突出临期与已过期项。 |
| 状态标识 | P0 | 已过期 / 7 天内到期 / 30 天内到期 / 充足 四档状态，颜色区分。阈值通过配置文件定义。 |
| 临期提醒 | P0 | 基于到期时间，在前端以醒目标识提示即将到期的订阅（MVP 阶段以页面提示为主，预留通知扩展）。 |
| 可视化统计 | P1（辅助） | **本阶段仅做"未来到期时间轴"一张图**，直接服务于"什么时候过期"的核心痛点。其余图表（月度支出分布、类别占比等）后置。 |
| 灵活部署 | P0 | 提供**快速部署**（无容器、嵌入式数据库，开箱即用）与**稳定部署**（MySQL 环境）两种方式，数据均保存在本地，无第三方云服务依赖，保障隐私。 |

### 1.5 技术架构概览

项目采用**单仓库前后端分离**结构：

- **前端**：Vue 3 + Vite + TypeScript，使用 Pinia 状态管理、Vue Router 路由、ECharts 图表、Day.js 时间处理。
- **后端**：Express 5 + TypeScript，提供 REST API，统一响应信封契约。
- **数据库（可切换）**：
  - **快速部署**：使用嵌入式数据库 **SQLite**（文件型，无需安装数据库服务，零外部依赖）；
  - **稳定部署**：使用 **MySQL 8.0**（通过 Docker Compose 或直接连接既有 MySQL 实例）。
  - 后端通过数据访问层（DAL）抽象屏蔽两种数据库的差异，业务代码不感知底层数据库类型。
- **配置驱动**：状态阈值、日期格式、货币符号等可调参数集中存放于配置文件（详见第 5 章），虽为硬编码但可随时修改，无需改动业务代码。

> **DAL 抽象风险提示**：SQLite 与 MySQL 存在方言差异（日期函数、自增主键、布尔类型、JSON 字段等），DAL 层需在开发期重点关注并充分测试，确保两种数据库行为一致。

### 1.6 范围说明

- **本期（MVP 第一阶段）范围**：
  - 面向**个人用户**的订阅增删改查、到期看板、临期页面提醒；
  - 单张可视化图表（未来到期时间轴）；
  - 两种本地部署方式（快速部署 / 稳定部署）；
  - 单用户、单实例的本地数据存储；
  - 软删除 + 归档机制。
- **非本期（MVP 第一阶段）范围**：
  - **小型团队多人协作**：多用户账户、登录鉴权、共享看板、成员权限管理、团队协作；
  - 邮件 / 短信 / Webhook 主动推送提醒；
  - 订阅自动抓取（对接第三方账单 API）；
  - 订阅自动续期 / 自动滚动周期（坚持手动维护原则）；
  - 数据导入 / 导出（CSV、JSON）；
  - 多币种与汇率转换（本阶段统一人民币）；
  - 月度支出统计及其口径定义；
  - 移动端原生应用。

## 2. 部署要求

产品需支持**纯本地部署**：数据保存在用户自有环境，不依赖任何第三方云服务，以保障隐私。为兼顾不同用户的机器环境，MVP 阶段要求提供两种部署模式：

| 部署模式 | 适用场景 | 容器环境 | 数据库 | 复杂度 |
|----------|----------|----------|--------|--------|
| **快速部署** | 个人本地试用，机器无 Docker / 容器，希望开箱即用 | 不需要 | SQLite（文件型，零依赖） | 低 |
| **稳定部署** | 具备 MySQL 环境（本机或已有实例），追求数据稳定性与可维护性 | 可选（推荐 Docker） | MySQL 8.0 | 中 |

**要求明细：**

- 两种模式共用同一套前端 / 后端代码，底层数据库类型对用户与业务代码透明，通过配置切换；
- 个人用户**默认推荐快速部署**，无需安装任何数据库服务即可运行，数据以单文件形式存放，便于备份与迁移；
- 当数据量增长或需要数据库级管理时，可切换至稳定部署；
- 部署过程对用户友好，安装 / 配置 / 启动步骤应最小化，降低个人本地使用的门槛。

> **部署模式切换路径（MVP 阶段）**：MVP 阶段不提供自动数据迁移工具。两种模式之间的数据迁移通过"未来版本提供导入/导出工具"实现，本阶段若需切换，需手动处理。自动迁移工具列入第二阶段规划。

> 具体的安装、配置与启动命令（如依赖安装、环境变量填写、Docker 编排、端口与故障排查）属于工程部署手册（README）范畴，不在本文档展开；开发 / 运维人员请参考仓库 README 与相关部署文档。

## 3. 功能需求

> 本章节定义 MVP 第一阶段的具体功能需求（FR）。每项含描述、关键规则与验收要点。

### 3.1 订阅管理

#### FR-01 订阅录入

- **描述**：用户手动添加一条订阅记录。
- **字段**（详见第 4 章数据模型）：
  - 名称（必填）
  - 类别（必填，关联自定义分类）
  - 价格（必填，单位：人民币元，`DECIMAL(10,2)`）
  - 计费周期（必填，枚举：月 / 季 / 年）
  - 开始日期（必填，`YYYY-MM-DD`）
  - 到期日期（必填，`YYYY-MM-DD`，**核心字段**，用于计算剩余天数）
  - 是否自动续费（必填，布尔，**仅作状态标记**，展示"下个月是否续费"，不触发任何自动逻辑）
  - 备注（选填，纯文本）
- **校验规则**：
  - 名称非空，长度 ≤ 100；
  - 价格为非负数字，精度 2 位小数；
  - 到期日期不得早于开始日期；
  - 若服务以非人民币计价，由用户**自行换算后填入**（录入界面需给出提示文案）。
- **三字段关系**：开始日期、到期日期、计费周期三者**独立填写**，系统不做自动推算；计费周期与开始日期仅作记录与展示参考，**到期日期为唯一权威字段**用于剩余天数计算。
- **验收**：可成功创建一条符合校验规则的订阅；违反规则时给出明确错误提示。

#### FR-02 订阅编辑

- **描述**：用户可编辑任意一条订阅的全部字段。
- **规则**：编辑时同样执行 FR-01 的校验规则；编辑后更新 `updated_at`。
- **验收**：字段可修改并保存；校验失败有提示。

#### FR-03 订阅删除（软删除 + 二次确认）

- **描述**：用户删除订阅时执行**软删除**（置 `deleted_at`，不在列表中展示），删除操作需**二次确认**。
- **规则**：
  - 删除前弹出确认弹窗，明确告知"将删除订阅 [名称]"；
  - 确认后置 `deleted_at = 当前时间`，数据保留在数据库；
  - 软删除记录不出现在默认看板，但保留可恢复能力（见 FR-04）。
- **验收**：删除有二次确认；删除后默认视图不可见；数据库中记录仍存在。

#### FR-04 订阅归档与恢复

- **描述**：已过期订阅可**归档**（不进入默认视图，但可恢复查看）；归档与软删除相互独立。
- **规则**：
  - 归档字段 `archived`（布尔，默认 false）；
  - 归档后订阅不出现在默认看板，可在"已归档"视图中查看；
  - 归档可逆，支持取消归档恢复到默认视图；
  - 软删除的记录同样可恢复（清空 `deleted_at`）。
- **验收**：归档/恢复操作生效；"已归档"视图可见归档项；软删除可恢复。

### 3.2 到期看板

#### FR-05 看板展示与排序

- **描述**：以卡片 / 列表形式展示所有**未软删除、未归档**的订阅，默认按"剩余天数"升序排序（临期靠前）。
- **规则**：
  - 每张卡片展示：名称、类别、价格、计费周期、到期日期、剩余天数、状态徽章、是否自动续费标记；
  - 已过期项置顶或独立分区展示；
  - 预期数据量：几十 ~ 100 条，**无需分页 / 虚拟滚动**。
- **验收**：默认视图按剩余天数升序；已过期项突出展示。

#### FR-06 状态四档标识

- **描述**：按剩余天数将订阅标记为四档状态，颜色区分。
- **阈值**（通过配置文件定义，详见第 5 章）：
  - **已过期**：剩余天数 < 0（到期日期早于今天）
  - **7 天内到期**：0 ≤ 剩余天数 ≤ 7
  - **30 天内到期**：8 ≤ 剩余天数 ≤ 30
  - **充足**：剩余天数 > 30
- **边界**：剩余天数按**整天取整**（到期日期 − 今天，不含时分）；恰好为 0 归入"7 天内到期"。
- **颜色映射**：由设计令牌统一管理（详见 7.2），如：已过期=红、7天=橙、30天=黄、充足=灰/绿。
- **验收**：四档状态颜色正确；边界值归类正确。

#### FR-07 筛选与搜索（可选）

- **描述**：支持按类别筛选、按名称搜索、按状态筛选。
- **优先级**：因数据量小，**可列为 P1 可选项**，开发资源允许时实现。
- **验收**：筛选 / 搜索结果正确。

### 3.3 临期提醒

#### FR-08 页面醒目标识

- **描述**：临期订阅（7 天内 / 已过期）在看板上以醒目样式标识（颜色、图标、置顶）。
- **规则**：MVP 阶段仅做**前端页面提示**，不做邮件 / 短信 / Webhook 推送；通知渠道扩展预留接口，列入第二阶段。
- **验收**：临期项视觉醒目；阈值可通过配置调整。

### 3.4 可视化统计（辅助特性）

#### FR-09 未来到期时间轴

- **描述**：以时间轴 / 甘特图形式展示未来一段时间内到期的订阅分布。
- **范围**：默认展示未来 90 天（可通过配置调整）。
- **规则**：仅展示未软删除、未归档订阅；点击节点可跳转到对应订阅详情。
- **优先级**：**P1 辅助特性**，服务于"什么时候过期"的核心痛点。
- **验收**：时间轴正确反映到期分布；可点击跳转。
- **后置图表**：月度支出分布、类别占比等列入第二阶段（见 9.2）。

### 3.5 分类管理

#### FR-10 自定义分类

- **描述**：用户可自定义订阅分类（无预设分类，最大化通用性）。
- **规则**：
  - 分类独立管理（增删改）；
  - 删除分类时，引用该分类的订阅处理策略：**禁止删除已被引用的分类**，提示用户先迁移或重分类相关订阅；
  - 分类名称非空，长度 ≤ 50，同一用户下唯一。
- **验收**：分类可增删改；删除被引用分类时有明确提示。

## 4. 数据模型

> 本章节定义核心实体字段。类型标注兼顾 SQLite / MySQL，具体 SQL 方言映射由 DAL 层处理。

### 4.1 订阅实体 `subscription`

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `id` | INTEGER（自增主键） | 是 | - | 主键 |
| `name` | VARCHAR(100) | 是 | - | 订阅名称 |
| `category_id` | INTEGER（外键） | 是 | - | 关联 `category.id` |
| `price` | DECIMAL(10,2) | 是 | - | 价格，单位：人民币元 |
| `billing_cycle` | VARCHAR(16) | 是 | - | 枚举：`month` / `quarter` / `year` |
| `start_date` | DATE | 是 | - | 开始日期 `YYYY-MM-DD` |
| `expire_date` | DATE | 是 | - | **到期日期（核心字段）** |
| `auto_renew` | BOOLEAN | 是 | `false` | 是否自动续费（**纯标记**，不触发自动逻辑） |
| `note` | TEXT | 否 | NULL | 备注 |
| `archived` | BOOLEAN | 是 | `false` | 是否归档 |
| `deleted_at` | TIMESTAMP | 否 | NULL | 软删除时间，NULL 表示未删除 |
| `created_at` | TIMESTAMP | 是 | 当前时间 | 创建时间 |
| `updated_at` | TIMESTAMP | 是 | 当前时间 | 更新时间 |

### 4.2 分类实体 `category`

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `id` | INTEGER（自增主键） | 是 | - | 主键 |
| `name` | VARCHAR(50) | 是 | - | 分类名称，唯一 |
| `created_at` | TIMESTAMP | 是 | 当前时间 | 创建时间 |
| `updated_at` | TIMESTAMP | 是 | 当前时间 | 更新时间 |

> 分类不做软删除：删除前需确保无订阅引用（见 FR-10）。

### 4.3 软删除与归档查询约定

- **默认视图查询条件**：`deleted_at IS NULL AND archived = false`；
- **已归档视图查询条件**：`deleted_at IS NULL AND archived = true`；
- **已删除视图（恢复用）查询条件**：`deleted_at IS NOT NULL`。

## 5. 配置项

> 可调参数集中存放于配置文件（前后端各有一份对应配置，保持一致）。虽为硬编码，但修改配置无需改动业务代码。

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| `statusThresholds.soon7` | 7 天内到期阈值（天） | `7` |
| `statusThresholds.soon30` | 30 天内到期阈值（天） | `30` |
| `timeline.rangeDays` | 未来到期时间轴展示范围（天） | `90` |
| `dateFormat` | 日期展示格式 | `YYYY-MM-DD` |
| `currencySymbol` | 货币符号 | `¥` |
| `timezone` | 时区处理（默认本地） | `local` |

> 状态阈值定义：剩余天数 < 0 → 已过期；0 ~ `soon7` → 7 天内；`soon7+1` ~ `soon30` → 30 天内；> `soon30` → 充足。

## 6. 非功能需求

### 6.1 性能与容量

- 预期数据量：几十 ~ 100 条订阅；
- 无需分页 / 虚拟滚动；
- 看板首屏渲染应流畅，列表与图表加载无明显延迟。

### 6.2 兼容性

- 目标浏览器：Chrome / Edge / Firefox / Safari 最新版；
- Web 端是否需要响应式（手机浏览器访问）：**MVP 阶段以桌面端为主**，响应式适配列入第二阶段。

### 6.3 数据安全与备份

- 数据保存在本地，无第三方云服务依赖；
- SQLite 单文件存在损坏风险，MVP 阶段不提供自动备份机制，依赖用户手动备份数据库文件；
- 备份/恢复工具（导入/导出）列入第二阶段。

### 6.4 国际化

- MVP 阶段仅支持中文界面，国际化框架预留但不实现。

## 7. 工程规范

> 本章节约束项目目录结构、公共样式、公共组件与接口扩展原则，目的是**保持视觉一致性、减少重复造轮子、降低维护成本**。

### 7.1 目录结构规范

项目采用单仓库前后端分离，推荐结构如下（已有结构基础上规范化）：

```
exp-track/
├── backend/                       # 后端
│   └── src/
│       ├── config/                # 配置项（状态阈值等，对应第 5 章）
│       ├── dal/                  # 数据访问层（SQLite/MySQL 抽象）
│       ├── routes/               # 路由定义
│       ├── controllers/          # 控制器（请求/响应处理）
│       ├── services/             # 业务逻辑
│       ├── middlewares/          # 中间件
│       ├── types/                # 共享类型
│       ├── utils/                # 工具函数
│       └── app.ts                # 应用入口
├── src/                           # 前端
│   ├── api/                      # 接口封装（统一调用入口）
│   ├── assets/
│   │   └── styles/               # 公共样式、设计令牌
│   ├── components/               # 公共组件
│   │   └── base/                 # 基础原子组件（按钮、输入框等）
│   ├── composables/              # 组合式函数
│   ├── layouts/                  # 布局组件
│   ├── router/                   # 路由
│   ├── stores/                   # Pinia 状态管理
│   ├── views/                    # 页面
│   ├── types/                    # 类型定义
│   └── utils/                    # 工具函数
├── shared/                       # 前后端共享类型（可选，推荐）
└── ...
```

**约束**：

- 公共能力（样式、组件、工具函数、类型）按上述目录归口，**禁止在业务页面内重复定义同类能力**；
- 新增文件须放入对应目录，避免随意放置。

### 7.2 公共样式与设计令牌

- **设计令牌（CSS 变量）**统一在 `src/assets/styles/` 下定义，至少包含：
  - 色彩（主色、状态色、中性色）；
  - 间距（spacing scale）；
  - 圆角、阴影；
  - 字号、行高。
- **状态色映射**（与 FR-06 四档状态对应）必须由设计令牌统一管理，禁止在组件内硬编码颜色值：

| 状态 | 建议色 |
|------|--------|
| 已过期 | 红 |
| 7 天内到期 | 橙 |
| 30 天内到期 | 黄 |
| 充足 | 灰/绿 |

- 全局基础样式（reset、排版）统一管理，业务组件样式仅写自身差异化部分。

### 7.3 公共组件

- 重复出现的 UI 单元**必须抽取为公共组件**，放入 `src/components/`（基础原子组件放 `base/`）；
- 本阶段应抽取的公共组件（不限于）：
  - `StatusBadge`：状态徽章（四档色统一，复用设计令牌）
  - `SubscriptionCard`：订阅卡片
  - `CategoryTag`：分类标签
  - `ConfirmDialog`：确认弹窗（删除二次确认复用）
  - `EmptyState`：空状态
  - 通用表单控件封装
- 公共组件应** props 驱动、无副作用**，便于复用与测试。

### 7.4 视觉一致性原则

- 同类元素（按钮、卡片、徽章、间距）全站视觉统一；
- 颜色、间距、圆角、字号**只能使用设计令牌**，禁止散落硬编码；
- 新增页面 / 组件须复用既有公共组件，**减少重复造轮子**。

### 7.5 接口扩展原则（重点）

> **核心原则：能对现有接口进行改造兼容的，不要新增接口。** 新增接口会增加维护难度与认知成本。

- **优先扩展现有接口**：新需求优先通过在现有端点上**新增可选字段 / 可选参数**实现，而非新增端点；
- **向后兼容**：新增字段只增不删，旧客户端不受影响；废弃字段需保留过渡期并标注；
- **统一响应信封**：所有接口遵循统一响应结构（如 `{ code, message, data }`），不得为单个接口自定义格式；
- **RESTful 命名规范**：资源命名统一、动词语义清晰；
- **接口合并**：功能相近的查询接口优先合并（通过参数区分），避免端点爆炸；
- **新增接口需评估**：确需新增接口时，需评估是否能通过扩展现有接口达成，并记录决策原因。
